# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A persistent gladiator arena. A fixed roster with hidden stats fights a 1v1 duel every hour, one round per minute. Players stake virtual points on the **next** fight. Phase 2 is building this to replace the original "Higher or Lower" minute-roll game, which task 01 removed. It was never deployed.

- [docs/spec-arena.md](docs/spec-arena.md) (v3) is the source of truth for the arena's rules, data model and API. Read the relevant section before implementing a feature. Section 12 records the settled decisions, so build on them rather than reopening them.
- [docs/tasks-phase-2.md](docs/tasks-phase-2.md) lists the ordered arena tasks (01–12) and what blocks each one. The full ticket for each task, with acceptance criteria, is in `.scratch/arena/issues/`. Read the ticket before starting a task, build it test-first, and keep both files current as tasks land.
- [docs/tasks-production.md](docs/tasks-production.md) is the backlog for making the arena safe to deploy (P1–P8). None of it has started.
- [docs/spec-higher-or-lower.md](docs/spec-higher-or-lower.md) (v2) describes the old game. It's history only: none of its code remains.

**Arena rules that cause real bugs** (details in spec-arena.md):

- Hidden stats (`hp`, `attack_*`, `defence`, `agility`) never leave the `gladiator` and `fight` features: no API, page, event or log line. The real roster file stays out of git.
- Odds come from public Elo only, are stored on the fight at announcement, and are copied onto each bet. Only `p_red_bps` uses floating point. Everything else is integer maths.
- A fight's seed and each round's raw rolls are internal, like the stats. They're logged for fact-checking but never published. Rounds come from `HMAC(seed, "<fight_id>:<n>:<corner>:<kind>:<c>")` with rejection sampling, so a fight replays exactly from its seed.
- After a crash the engine resumes the fight from its row and replays overdue rounds. It never voids a fight.
- Ledger reasons are v2's (`stake`, `payout`, `refund`, …), with `ref_id` = bet id.
- The fight engine is idempotent on `announced → live → settled` and `rounds_done`, under its own advisory lock. Dev forcing only pulls due times forward and then calls the real `tick()`.
- Bets: `payout = floor(stake × multiplier_bps / 10000)`, stake included, capped at `game.max-payout` (10,000). A draw refunds the stake (`push`). Settlement is set-based SQL (1,000 bets in under 2s), and events reach clients only after commit (`@TransactionalEventListener`).
- **Points** (spec §2): points are virtual and can never be bought or cashed out. Store them as `BIGINT`. Every wallet change writes a ledger row (`delta`, `reason`, `ref_id`), keeping the invariant `balance = SUM(ledger.delta)`. Debit stakes with a conditional atomic `UPDATE … WHERE balance >= :stake`.

## Implementation notes

Arena code follows these patterns: feature services, `GameRuleException`, the board value, events after commit, `TestGame`. When code and the spec disagree, the spec wins.

- **Settings:** `GameProperties` (`game.*`), with production defaults in the record's `@DefaultValue`s. Its constructor refuses to start the app on bad settings (a stake button outside the limits, or a capped fight that doesn't fit between two `fight-cron` slots). Environment variables override any key (`GAME_ROUND_INTERVAL=5s`), and `.env.example` lists them all. Compose loads `${ENV_FILE:-.env}`. The dev cadence lives in `application-dev.properties`, and `.env.dev` only sets `SPRING_PROFILES_ACTIVE=dev` for compose.
- **Dev profile:** `FightForcing` (fight feature) and `dev.DevController` (`POST /dev/fights/{start,round,finish}`) exist only under `@Profile("dev")`. They pull a due time forward and call the real `tick()`. The board shows the dev panel to logged-in viewers under the dev profile. `fight.DevRatings` (dev profile too) seeds a fresh arena's ratings from a simulated season (`fight.EloSeason`) at startup. That is the only place ratings come from the hidden stats, so keep it out of production.
- **Auth:** `user.SecurityConfig` sets up form login (`/auth/login`, `/auth/signup`, `/auth/logout`), BCrypt and CSRF. Watching is public (`/`, `/fragments/board`, `/live`, `/fights/**`, `/gladiators/**`, `/leaderboard`), and everything else needs login. Logged-out callers get a 401 from the JSON API, a 401 with `HX-Redirect` from htmx, and the login page from a plain browser. `user.CurrentUser` gives the logged-in `GamePrincipal`, which carries the user id. `UserService.signup` creates the user and their wallet (signup bonus) together.
- **JSON API:** `web.GameApiController` serves `POST /bets` and `POST /wallet/topup`. Errors are ProblemDetails. Services refuse player requests with `GameRuleException.invalid(...)` (400) or `.conflict(...)` (409), and the page shows the same message inline. Any other exception is a bug and becomes a 500, so never use a `GameRuleException` for internal faults. JSON is snake_case, and enums serialise in lower case (`@JsonValue`).
- **Bets:** `bet.BetService.place` backs both `POST /bets` (JSON) and `POST /bet` (the board's stake buttons). `FightService.lockForBetting` share-locks the announced fight and refuses with 409 when betting has closed, or 400 when there is no such fight. `fight` alone decides whether betting is open: `AnnouncedFight.bettingOpen` is stamped from the same clock read, and the board copies it. It is `@JsonIgnore`d, because in a payload it would go stale. `bet.BetSettlement` settles a fight's bets in set-based SQL. It is a plain `@EventListener` on `FightSettled`, so it runs inside the engine's tick and `fight` never calls `bet`. Payouts and refunds go through `WalletService.creditAll`, the wallet's one-statement batch credit (`WalletRepository.creditAll`), and the caller says who gets what.
- **Public pages:** `/fights`, `/fights/{id}`, `/gladiators`, `/gladiators/{slug}` and `/leaderboard` each have two handlers on one path, JSON and HTML, chosen by the `Accept` header (`produces`). They render public records only (`FightRecord`, `GladiatorProfile`, `LeaderboardEntry`). All viewer-facing text (result lines, round log lines, bet lines, odds, percentages) lives in the root `Wording`, shared by the board and the pages and tested without Spring in `WordingTests`. Callers decide which line to show and pass plain values, not records. Gladiator figures are computed in SQL in `fight.CareerRepository` from public columns of settled fights, as integers (rates in basis points, averages in hundredths). `NoLeakTests` sweeps every public response and a whole fight's SSE payloads for stat, seed and roll fields, so add any new public endpoint to it.
- **Live:** `/live` sends a `snapshot` event on connect (the `/fights/current` payload, which carries `server_time`). `ArenaBroadcasts` turns the engine's events into `matchup_announced`, `fight_started`, `round` and `fight_settled` after commit, and sends `bet_settled` to the bet's owner only. Its `@Order`s keep a tick's broadcasts ahead of its personal events, because bets settle while `FightSettled` is still being published. `LiveStreams` broadcasts to every stream, and sends a per-user event to that player's streams only, so anonymous streams get broadcasts only. Every send after the snapshot runs on the one `live-sender` thread (`LiveSender`).
- **Page:** `game.html` has one SSE connection and an htmx `board` fragment (`GET /fragments/board`), refetched on the snapshot and on every arena event. The board renders one `board.Board` value built by `BoardService` (plus a `BoardFeedback` for the last POST), so what a viewer sees, log lines and result wording included, is decided and tested there, not in the template. Countdowns are `data-until` instants, ticked by the page's script on the board's `data-server-time` offset. `POST /topup` and `POST /bet` return the board with any error inline. Keep page state inside the board, because anything outside it isn't refreshed. htmx sends the CSRF token from `<meta>` tags as a header. htmx and its SSE extension are pinned on unpkg with SRI hashes, so recompute the hash when bumping a version.
- **Theme:** every page links one stylesheet, `static/arena.css` (a torchlit Roman broadside; colours are tokens on `:root`), and the `fonts` fragment (Cinzel and EB Garamond from Google Fonts). `SecurityConfig` permits `/arena.css` by name. `game.html` holds the SVG defs the board uses (the `#brush` filter and the `#laurel-branch` behind each VS) outside the board, so they survive its swaps. Stake buttons are styled as coins whose metal comes from their position (copper, silver, then gold). The board is two boxes of one fixed height, side by side on a wide screen and stacked on a phone: the fight in the sand (live, or the last result) as a dark panel, and the next fight as a cream bill nailed to the wall (`--bill-*` tokens). Anything that comes and goes (a bet, the stake buttons, more rounds) changes inside its box, so the page keeps its shape.

**Tests:** Spring test classes use `@GameTest`, so they share one context and Postgres container. `TestGame` (`@Autowired`) drives the game: `boot`, `startFight`, `nextRound`, `finishFight` and `plantFight` move the `MutableClock` and tick the real engine. Dev-profile tests use `@DevGameTest`, which shares one more context and pins the cadence back to production over the dev profile's fast one. The wallet repositories are package-private, so tests that need an unusual balance go through the `wallet.TestWallets` bean, which writes each change's ledger row. Test classes that change balances check every wallet against its ledger after each test. Test classes that commit clear the arena with `TestFights.deleteAll`, which truncates `bets` along with the fights. Each test class signs up its own player (`TestPlayers.signUp`). MockMvc calls that need a login use `.with(user(player))`, and POSTs add `.with(csrf())`. Test-only settings go in `src/test/resources/config/application.properties`, which overrides individual keys from the main `application.properties`. Don't create `src/test/resources/application.properties`: it would replace the main file entirely.

Database gotchas: a trigger makes `ledger` append-only. Nothing is deployed yet, so a migration may still be edited in place. After deleting, renaming or editing a migration, run `./mvnw clean` (Flyway also sees stale copies in `target/classes`) and `docker compose down -v`.

## Stack

This is a **full-stack Spring Boot application**: one app, with its Maven project at the repo root, serves both the UI and the API. The UI is Thymeleaf plus htmx with no JS build step. Live updates go over SSE from the same app. The module uses Spring Boot 4.1.1, Java 21, Maven, Spring Web MVC, Spring Data JDBC (no JPA), Flyway and PostgreSQL, under the package `com.rdavies.arena`. Ask before adding new infrastructure (Redis, Lambda and so on). The spec deliberately runs without both.

Packages are organised **by feature**: `wallet`, `user`, `board`, `live` and `web` now, joined in Phase 2 by `gladiator`, `fight`, `bet`, `dev` and `leaderboard`. Inside a feature, data types go in sub-packages by kind: records in `<feature>.records` (e.g. `wallet.records.Wallet`, `fight.records.RoundResult`) and enums in `<feature>.enums` (e.g. `fight.enums.Corner`). Nested types stay nested (`LedgerEntry.Reason`, `GameApiController.TopUp`). Services, repositories, rules (`fight.Combat`, `fight.FightRolls`) and config stay at the feature root, so package-private still guards them: the wallet repositories are package-private so only `WalletService` changes a balance, and nothing outside `fight` can reach the seed or the rolls. Each feature has its own service. Controllers in `web` call those services, never repositories. Each feature's SQL touches only its own tables (`bet` never reads `wallets`, `wallet` never reads `bets`), and data crosses features through service calls. Feature services use repositories, not `JdbcTemplate`. Prefer derived queries (`@Lock` for row locks) and keep `@Query` SQL for what they can't express. `@Query` binds a Java array (`Long[]`, `String[]`) as a Postgres array, so a batch goes in as parallel arrays and `unnest(CAST(:ids AS bigint[]), …)` (see `WalletRepository.creditAll`). Write `CAST(:x AS …)`, not `:x::…`, and pass an array, not a `List`, which expands to an `IN` list. Raw JDBC in a repository fragment is the last resort, for what `@Query` can't do.

All time logic reads the injected `java.time.Clock` bean. Tests swap it for a `MutableClock`.

## Commands

Run these from the repo root. Use `./mvnw` in Git Bash, or `mvnw.cmd` in PowerShell.

```bash
./mvnw spring-boot:run
./mvnw test
./mvnw test -Dtest=WalletTests                          # single class
./mvnw test -Dtest=WalletTests#topUpIsOncePerUtcDay     # single method
./mvnw package
```

`docker compose up --build` starts Postgres 15 and the app on port 8080.

Dev mode (a fight every 3 minutes, 5s rounds, the dev panel) is the `dev` profile. Under compose it needs a local `.env.dev` (gitignored) holding `SPRING_PROFILES_ACTIVE=dev`. Run `ENV_FILE=.env.dev docker compose up --build` (in PowerShell: `$env:ENV_FILE = ".env.dev"; docker compose up --build`), or `docker compose up db` plus `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev` with `SPRING_DATASOURCE_*` pointing at `localhost:5432`. No linter or formatter is configured.

**Datasource:** `application.properties` sets only the app name and the JSON naming. Running the app needs `SPRING_DATASOURCE_*` pointing at PostgreSQL, which `docker-compose.yml` provides. Tests get Postgres from Testcontainers (`TestcontainersConfiguration`, imported by `@GameTest`), so Docker must be running. A test that takes an advisory lock from another thread must not be `@Transactional`, because the test transaction would hold the lock itself and deadlock.
